Not Every Prompt Takes The Same Route

The workflow expands or contracts according to what could change or go wrong.

A Question Or Explanation

I investigate and answer. No repository change means no worktree, commit, or deployment.

A Visible App Change

I use the full route: isolate, build, test, photograph, deploy, and verify the live experience.

A Risky Or Foundational Change

Data, privacy, text messaging, and shared architecture receive deeper investigation and more proof.

The Workflow By Category

Open a category to translate the behind-the-scenes activity into plain English.

01 Understand The Outcome From Prompt To A Clear Definition Of Done

What I Do

I identify the desired result, audience, affected screen or behavior, boundaries, and whether you want an explanation, diagnosis, or completed change.

Why We Do It

A technically correct answer to the wrong problem is still wrong. A concrete finish line keeps implementation choices aligned with your real goal.

Help Me By Saying

What should be different, who should notice it, what must stay the same, and any wording or visual direction you already know you want.

02 Protect And Isolate The Work A Safe Workspace For Every Change

What I Do

I create a separate Git worktree and branch for the prompt. It has its own files, change history, and place in the completion queue.

Why We Do It

Two ideas can be built at once without overwriting each other, sharing unfinished files, fighting over the Git index, or deploying the wrong work.

Parallel Development

Separate work happens in parallel. Shared steps—integrating with the latest main branch, restarting port 3002, and deploying—wait in a serialized queue.

03 Investigate The Current System How This Part Of IN or OUT Works Today

What I Do

  • Read the project rules and related code.
  • Trace connected screens, APIs, data, and tests.
  • Check current behavior when memory or old notes are not proof.

Why We Do It

A text message might also be randomized, stored in a database, shown in a preview, sent through an SMS provider, and counted in Developer Area metrics.

Help Me By Saying

Where you saw the behavior, the steps that led to it, and whether the change should affect existing data or only things created in the future.

04 Plan And Build The Change The Smallest Complete Change For The Whole Product

What I Do

I choose the files and approach, preserve existing architecture, implement the behavior, and cover related states such as loading, empty, error, desktop, mobile, and keyboard use when relevant.

Why We Do It

The goal is not merely to make one screenshot look right. The change must belong in the app, remain understandable, and avoid surprising another flow.

What You May See

I may revise the approach after discovering a dependency. That is the investigation doing its job, not the prompt being ignored.

05 Test At The Right Layers Different Questions At Different Layers

What Testing Means

Testing is controlled evidence. I give the software a known situation, observe what it does, and compare that result with the behavior we intended.

Why There Are Many Tests

A spelling check cannot prove a button saves. A unit test cannot prove a page renders. A local browser cannot prove the new production server is live.

How Much Testing

I choose tests in proportion to the change. A copy edit needs less behavioral coverage than roster ordering, privacy, image deletion, or text-message delivery.

Fastest Feedback Static Checks

Is the code valid and consistent with formatting, capitalization, and project rules?

Small Logic Unit Tests

Given specific inputs, does one function or rule return the exact expected result?

Connected Pieces Integration Tests

Do the route, database, permissions, and outside-service boundaries work together?

Real Interaction Browser Tests

Can a person open the page, click the control, complete the flow, and see the result?

Visual Evidence Screenshot Checks

Does the changed screen appear correctly at its real size, including important states?

Ship Readiness Deployment Gate

Does the complete required suite pass before this change is allowed to reach main?

Safety Boundaries Fixture Protection

Are test data, fake 555 numbers, local SQLite, and disabled real SMS kept away from production?

Live Proof Production Verification

Did a fresh server start, is it healthy, and does inorout.club now perform the changed behavior?

Human Judgment Review

Even when checks pass, does the result make sense, read naturally, and solve your request?

06 Document What Users Will See A Current Visual Record Of Screens And States

What I Do

For visible changes, I update the automated Screens capture when needed, regenerate the gallery, and verify it through Developer Area → Screens.

Why We Do It

The gallery is a visual map of the current product. It helps us review consistency, remember hidden flows, and see what the code actually produces.

When It Is Skipped

A truly server-only change with no visible surface does not need new screenshots, though it still needs relevant behavior and production checks.

07 Integrate And Deploy Safely One Guarded Lane For Shared Completion Work

What I Do

The completion workflow updates the isolated change with the latest main branch, runs the deployment gate, prepares the local app, merges, pushes both repositories, and triggers Render.

Why We Do It

The codebase may have moved while this prompt was being built. Rechecking after integration prevents two individually good changes from becoming one broken release.

Why There Can Be A Wait

Only one task can merge, restart the shared local server, publish Screens, and deploy at a time. Other tasks keep building while that shared lane is occupied.

Why a tiny text change can still take time: the edit is tiny, but isolation, checks, current Screens, integration, deployment, a fresh production process, and live proof are fixed completion work. The smaller code change does not make those safety promises disappear.
08 Verify Production And Report Back Proof Where You And Your Players Use The App

What I Do

I wait for a new production start time, check health, exercise the affected live behavior, confirm the live Screens publication when visible, and inspect failures if anything disagrees.

Why We Do It

A successful push says code arrived at a repository. It does not prove the host deployed it, the process restarted, or the public app behaves correctly.

What I Tell You

The outcome first: what changed, what important checks passed, whether it is live, and anything you should know or decide next.

A Better Prompt Has Five Useful Ingredients

You do not need technical language. Product context is often more valuable than code instructions.

01 Outcome

What should be true when the work is finished?

02 Place And Audience

Where does it happen, and who is using it?

03 Behavior Or Copy

What should the person see, do, or understand?

04 Boundaries

What should not change, or what is out of scope?

05 Proof

How would you personally know it works?

Example Prompt

“On the host’s Players tab, add a short note above the waitlist explaining that players move up automatically when a spot opens. Keep the existing controls and text-message behavior unchanged. It should read naturally on both phone and desktop.”

You do not have to specify the implementation. Tell me the outcome and the human reason behind it. I can investigate the safest way to build it. Exact copy, examples, screenshots, priorities, and “please do not change” boundaries are welcome whenever you have them.

The Rules We Build By

The current guardrails established while building and operating IN or OUT. These cover how changes ship, how the app should look, and the safety promises future work must preserve.

41 Current Rules
This is a living reference. When a standing rule changes, update this tab and its repository source together so the written rule and the actual workflow stay aligned.

Building And Shipping

8 Rules
  1. 01
    Prove Every Change As A User

    Run the app locally and exercise the affected page, control, or full flow. Passing unit tests alone is not enough for a user-facing change.

  2. 02
    Run The Checks That Cover The Change

    Use the relevant verification scripts, and always pass npm run verify:deploy before a completed change is committed.

  3. 03
    Use Port 3002 For The Local App

    Port 3001 belongs to another project. Resolve the listener on exactly 3002 and never stop an unidentified Node process.

  4. 04
    Restart After A Completed App Update

    Stop only the IN or OUT process on port 3002, start PORT=3002 npm start, and confirm the local health endpoint and changed behavior.

  5. 05
    Commit Completed Changes On Main

    Unless Scott says otherwise, a finished app change is committed. The post-commit workflow verifies it and pushes both repository remotes.

  6. 06
    Treat The Upstream Push As The Deploy

    Production builds automatically from the upstream main branch. Never push unfinished or unverified work there.

  7. 07
    Verify The New Production Process

    Wait for a new server start time, check production health, and exercise the affected behavior on inorout.club before calling the work complete.

  8. 08
    Use The Manual Deploy Hook Only As A Fallback

    Use it only when the automatic deployment did not start, failed, stayed on the previous version, or Scott asks for an additional restart.

Documentation And The Developer Area

5 Rules
  1. 09
    Refresh Screens After Every Visible Change

    Run npm run docs whenever copy, styles, layout, controls, screens, or user flows change.

  2. 10
    Photograph Every Changed State

    If the Screens gallery does not already cover the changed state, add it to scripts/capture-screens.js.

  3. 11
    Publish And Check Screens Locally And Live

    Publish locally before the commit and verify through Developer Area → Screens. After deployment, publish production and confirm the new timestamp and gallery.

  4. 12
    Leave The Old Artifact Copies Alone

    The Developer Area copies are the maintained reference. Do not republish the older external artifact pages unless Scott asks.

  5. 13
    Keep The Developer Area Private And Useful

    Leave it unlisted and password protected. Keep shipped ideas current, and keep the global error reporter fail-silent so reporting can never break a player page.

Interface And Content

9 Rules
  1. 14
    Capitalize Every Word In Authored UI Titles

    Titles, headings, tabs, short labels, card titles, option titles, and button labels capitalize every word, including short words.

  2. 15
    Preserve Intentional Product And Acronym Casing

    Keep SMS, DUPR, and API as acronyms, and preserve the product styling “IN or OUT.”

  3. 16
    Keep Explanatory Copy In Normal Sentence Case

    Help text, full sentences, placeholders, and user-provided content should read naturally rather than use title capitalization.

  4. 17
    Use Only The Six Court Classic Base Colors

    Brand, Ink, Canvas, Surface, Warning, and Danger are the base palette. Derive every other tone through opacity or color mixing.

  5. 18
    Give Every Color One Job

    Brand means action, selection, focus, or success; Warning means attention; Danger is reserved for destructive actions and errors.

  6. 19
    Keep A Clear Button Hierarchy

    Use one primary action per section. Secondary supports, Danger destroys, and Quiet goes back, cancels, or dismisses.

  7. 20
    Use Only Three Button Sizes

    Compact is 36 px on dense desktop rows, Standard is 44 px, and Large is 52 px. Compact controls become at least 44 px on small screens.

  8. 21
    Make Forms And Focus Consistent

    Controls share heights, radii, visible labels, error treatment, and an obvious keyboard focus state.

  9. 22
    Keep Status Color Small And Meaningful

    Use concise messages, badges, icons, or borders. Large panels remain neutral instead of being filled with status color.

Architecture, Data, And Privacy

6 Rules
  1. 23
    Keep The App Login-Free For Players And Hosts

    IN or OUT is a lightweight tool for friends. Public game links and private host management links replace user accounts.

  2. 24
    Keep Local And Production Data Separate

    Local development uses SQLite. Production uses PostgreSQL. Fixture scripts must refuse to create or delete data when that boundary is uncertain.

  3. 25
    Never Expose The Host Token Publicly

    The public game endpoint and player pages must not reveal the private credential that controls a game.

  4. 26
    Keep Host Notes And Roster Details Private

    Host notes, host-entered names, and DUPR details belong to the host and must not appear on player-facing pages.

  5. 27
    Require Host Authorization For Destructive And Media Actions

    Uploading, selecting, clearing, or deleting images—and changing protected game data—requires the correct host credential.

  6. 28
    Remember The Single-Process Lock Boundary

    The per-game lock is safe only while production runs one Node instance. Scaling out requires moving write ordering into the database first.

Automated Test Safety

7 Rules
  1. 29
    Never Send A Real Text From An Automated Test

    Use players without phone numbers whenever possible, and blank the Textbelt key for every test or capture that needs phone numbers.

  2. 30
    Double-Guard SMS Failure Tests

    Use both simulated failure and a blank Textbelt key, and never point the SMS failure verification scripts at production.

  3. 31
    Run Screenshot Fixtures Only On Local SQLite

    The documentation server must reject a production database, use a free port, use reserved 555 numbers, and keep SMS in development mode.

  4. 32
    Clean Up Fixtures Even When A Capture Fails

    Fixture teardown must run after partial failures and match both a marker and reserved phone numbers so it cannot remove a real game.

  5. 33
    Space Out Production Verification Runs

    Run production integration checks one at a time. Production rate limits can turn a safe burst into misleading 429 responses.

  6. 34
    Make Production Cleanup Narrow And Reversible

    Start with a dry run, refuse candidates with phone numbers or reminder history, and write a timestamped backup before deleting anything.

  7. 35
    Trust Verified Behavior Over Old Notes

    Historical project notes are context, not proof. Check the current code, tests, and live system before relying on a claim.

Core Behavior Safeguards

6 Rules
  1. 36
    Never Lose, Duplicate, Or Overbook A Player

    Concurrent actions must preserve every signup, keep the confirmed roster within capacity, and never place one person on both the roster and waitlist.

  2. 37
    Keep Promotion Rules Consistent

    First-come games may automatically promote the next waitlisted player. Approval games leave that decision to the host.

  3. 38
    Send Each Reminder Once, Including Catch-Ups

    Missed reminders can catch up before game time, late joiners still get theirs, and restarts or overlapping checks must not create duplicates.

  4. 39
    Save The User Action Even If Its Text Fails

    A failed confirmation must not erase a signup or cancellation. Retry a transient failure once, do not retry permanent errors, and tell the user the truth.

  5. 40
    Make Cancellation Idempotent

    A cancellation removes only the intended player. Repeating the same cancellation must not remove somebody else.

  6. 41
    Trust Image Bytes, Not File Claims

    Validate uploaded image types from their magic bytes, preserve exact bytes through storage, enforce limits, and keep upload and deletion host-only.

Six Base Colors, Each With One Job
